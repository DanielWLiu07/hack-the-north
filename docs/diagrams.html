The Elastic layer, drawn

Every place Elasticsearch touches the system: what it stores, how space and time are keyed, and where a query turns into a robot moving a physical object.

git — write path, source of truth Elasticsearch — read path, agent context robot — physical actuator disk — bytes too big to index

01 · Architecture

Git writes, Elasticsearch reads, the robot acts

Git holds the clean quantized truth and the transactional semantics — commits, branches, three-way merge. It cannot do semantic search, aggregations, spatial queries, or fuzzy time. So the same capture feeds two stores with opposite jobs, and the agent draws on both.

02 · Storage

Four orders of magnitude, four destinations

Raw point cloud points never enter Elasticsearch — a single capture is millions of them, and no useful question has the answer “point #4,812,003”. Each tier of data goes where its size and access pattern belong.

03 · Data model

Five indices, two access patterns, one join key

Elasticsearch has no joins, so the octree key is denormalized onto both the object and the voxel document. That is the intended pattern, not a workaround.

04 · Spatial keys

A prefix is a region — geohash with one more axis

Geohash interleaves the bits of latitude and longitude so nearby points share a prefix. The 3D version interleaves x, y and z: each base-8 digit carries exactly one bit per axis, so cells stay cubic at every level. Truncate the string, get a bigger cube.

The asymmetry that catches people: prefix → region is exact and free. Region → prefix is not — an arbitrary query box rarely aligns to the grid and needs a cover of several prefixes at mixed levels. Grid-aligned questions use the prefix; arbitrary geometry uses a shape query on the point field. Keep both.

05 · Change detection

Every commit stores a full snapshot; the diff is computed

Exactly like git, which stores trees rather than deltas. An object leaving the room is a row that stops appearing — never a row that gets deleted. That single decision is what makes time travel cheap.

06 · Time

Three kinds of time, and the agent translates between them

Git's time has no clock — it has ancestry. Elasticsearch's has no branches — it has a timeline. Neither can answer a question posed in the other's terms, which is the cleanest justification for having both.

07 · Retrieval

BM25 and vectors fail in opposite directions

BM25 nails keys_7c2e and scores “ceramic cup” at zero when you search “mug”. Dense vectors do the reverse. The VLM describes the same object differently from every camera, so both failure modes are live at once — which is exactly why the brief asks for hybrid.

08 · Temporal search

Finding something that isn't here any more

Because nothing is ever deleted, searching the whole index searches all of time. Filtering by commit_sha is what narrows you to a moment — omniscience is the default, the present is the filter.

09 · Agent

Retrieval tools and action tools on the same bus

Agent Builder exposes its tools over MCP, and Bracket Bot already ships bracketbot-mcp. So both halves of the agent speak one protocol — and the last call in the chain moves a physical object.

10 · Constraints

Which queries may cross the network

Voxelize once in memory, then fork. The robot benefits from having the grid; Elasticsearch benefits from indexing it. They are independent — so the indexing can fail at 4am and the robot won't care.

11 · The full flow

Every Elasticsearch call in one cycle

A judge moves the mug; the robot puts it back. Five phases, four lanes. Elasticsearch enters only where the question is “what do we know from history?” — everything else stays local.
